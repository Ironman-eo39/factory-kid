# ARCHITECTURE — Kid-Bait Physics Toy

**Version:** 2.0 (2026-10-15). Stack changed per consolidated review: Godot 4.6 first,
Three.js+Rapier+CCapture as fallback.

## Stack
- **Engine:** Godot 4.6 (GDScript), Compatibility renderer (OpenGL — targets
  weak iGPUs; no Vulkan dependency on the ASUS).
- **Physics:** Jolt (default 3D engine in Godot 4.6), fixed 1/60 step,
  rigid bodies ONLY, CCD on fast destroyers (hammer/axe).
- **Recording:** Godot Movie Maker (`--write-movie out.avi --fixed-fps 30`),
  in-engine audio capture → ffmpeg → H.264 MP4.
- **Assets:** Kenney Car Kit (CC0) for vehicles; primitives-in-code for
  destroyers/obstacles/characters; glTF 2.0 for any Blender work.
- **Audio:** in-engine procedural impacts (AudioStreamGenerator) + imported
  Suno chant WAVs (his override) + TikTok free-to-use fallback.
- **Tooling:** Python/bash scripts for batch queue, ffmpeg transcode,
  tri-count lint, manifest validation.

## Why Godot (see DECISIONS.md ADR-001/ADR-002)
Offline rendering removes the 8GB shared-memory / GC-spike / thermal risk
instead of managing it. Movie Maker renders every frame regardless of
wall-clock time — dropped frames are structurally impossible, and the ASUS's
1080p landscape panel limitation (can't window-capture 1080×1920) is
sidestepped entirely. Claude's spike already verified 1080×1920 @30fps with
audio on Linux/software rendering; the ASUS `record.bat` gate confirms it on
the real machine.

## Modularity — the load-bearing design
Every piece of content is a **module**: a folder with a manifest. The core
never hardcodes content.

```
content/
  vehicles/        e.g. moon_car/, kenney_jeep/, ...
  destroyers/      e.g. giant_hammer/, battle_axe/, slap_hand/
  characters/      e.g. log_warrior/, sneaker_shark/
  obstacles/       e.g. lava_pit/, drain_pipe/, ramp/
  arenas/          e.g. day_arena/, moon_arena/
```

**Module contract** (every module folder):
- `module.json` — `{ id, type, display_name, version, author,
  root_scene, params_schema, tags }`
- `main.tscn` — root scene implementing the content interface:
  `get_spawn_transforms()`, `apply_params(dict)`, `get_tags()`.
- `params.json` (optional) — default param values (colors, sizes, timings).
- README-less: keep it code, not prose. One screenshot `preview.png`
  (generated by the render smoke test, not hand-made).

**ContentRegistry (autoload):** scans `content/*/`, validates manifests
(schema check + root-scene loads + interface present), exposes
`list(type)`, `spawn(id, params)`, `validate_all()`. Adding a new
character/obstacle/scene = new folder; registry self-test fails the build
if the contract breaks.

**Scenario presets:** `presets/*.json` — `{ arena_id, cast: [{module_id,
params}], destroyers: [...], camera_path, beats: [...], seed }`. Presets are
data, editable without code. The staging UI is a preset editor + record
button.

## Core systems
- **ScenarioRunner** — loads a preset, spawns via registry, drives the
  beats timeline (setup → tension → release), triggers destroyers,
  fires camera cuts, ends the take. Deterministic-ish: preset + seed
  recorded per take; Jolt non-determinism accepted (record multiple takes).
- **VariationEngine** — takes a preset and produces N varied siblings by
  sampling the param space (arena layout, obstacle combo, camera path,
  lighting tint, car colors/roster, destroyer type, beat timings, music
  slot). Every output video must differ on ≥4 axes (DESIGN.md).
- **Recorder** — wraps Movie Maker: builds the godot CLI invocation,
  verifies output resolution/audio/wall_avg, calls the ffmpeg transcode
  script. Single entry point: `tools/record.sh preset.json`.
- **CameraDirector** — wide / dramatic-low / follow-chase presets,
  impulse-scaled screen shake, per-beat cuts defined in the preset.
- **AudioSynth** — procedural impacts (boing/crash/splat/whistle) scaled by
  impulse; mixer buses: SFX / Chants / Music. Chant WAVs imported per preset.
- **BatchQueue** — `queue.json` → sequential renders (overnight on the
  ASUS; Xvfb+llvmpipe smoke renders on jarvish) → ffmpeg → done folder.

## Physics & rendering rules (hard)
- Fixed 1/60 physics step, 30fps recorded output. World scale in meters.
- ≤60 dynamic RigidBody3D per scene; CCD on fast destroyers.
- ≤3k tris/model, ≤100k tris/scene (tri_lint.py fails CI otherwise).
- Lambert-equivalent materials (StandardMaterial3D, roughness 1, no
  metallic), 1 DirectionalLight + 1 hemisphere (WorldEnvironment ambient),
  NO shadow maps — blob shadows (dark ellipse decal under bodies).
- Viewport 1080×1920, stretch mode `canvas_items`, aspect `expand`
  (verify the vertical-output path in the Phase 0 spike).

## UI-based testing on jarvish (his requirement)
Not lint-only. Three real rendering-based levels on the Linux box:
1. **Render smoke test** — headless run of a scenario scene; scripted
   `Input.parse_input_event` drives the staging UI; screenshots captured
   every N frames via viewport texture → PNG. **Muse reads the PNGs and
   verifies visuals** (cars present, faces on, hammer slams, squash
   visible). Under Xvfb + `--rendering-driver opengl3`.
2. **Interactive staging pass** — scripted walkthrough of the staging UI
   (browse modules → load preset → tweak param → record 5s) with
   screenshots at each step; Muse inspects for breakage.
3. **His manual playtest** — each phase ends with Urbish running the build
   on the ASUS himself (playbook rule); plus the Phase 0 `record.bat` gate.

## Fallback path
If Phase 0 fails on the ASUS: Three.js + Rapier (SIMD WASM) +
CCapture WebCodecs build, same module contract ported to JS, same
presets. The variation system, IP rules, and pipeline are engine-agnostic
by design.
